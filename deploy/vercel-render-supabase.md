# Free-tier deployment: Vercel + Render + Supabase / الرفع المجاني: Vercel + Render + Supabase

Each Pro app is split in three, all on free plans. This is the alternative to the single-server setup in [README.md](README.md).
كل تطبيق من تطبيقات Pro ينقسم لثلاثة أجزاء على خطط مجانية. وهذا بديل للسيرفر الواحد في [README.md](README.md).

```
visitor ─▶ Vercel (Angular files)  ──/api, /swagger-ui, /actuator/health──▶ Render (Spring Boot API, ghcr.io image) ─▶ Supabase (PostgreSQL)
           <repo>.vercel.app          rewrite, browser still sees one origin   <repo>-api.onrender.com                   one project, one schema per app
```

| App / التطبيق | Vercel project | Render service | Supabase schema |
|---|---|---|---|
| Masar Pro | `masar-pro` | `masar-pro-api` | `masar` |
| StockMate Pro | `stockmate-pro` | `stockmate-pro-api` | `stockmate` |
| ClientFlow Pro | `clientflow-pro` | `clientflow-pro-api` | `clientflow` |

`render.yaml` (repo root) and `frontend/vercel.json` already use these names. If Vercel or Render gives you a different name because
yours is taken, change the Vercel address in `PUBLIC_URL` / `CORS_ORIGINS` (Render, Environment tab) and the Render address in
`frontend/vercel.json`. / لو Vercel أو Render سمّى مشروعك باسم ثاني لأن الاسم محجوز، غيّر عنوان Vercel في `PUBLIC_URL` و`CORS_ORIGINS`
(في Render) وعنوان Render في `frontend/vercel.json`.

## Steps / الخطوات

1. **Supabase** (once for all three apps). Create one project. Open *Connect* and copy the **Session pooler** details: host
   `aws-…pooler.supabase.com`, port `5432`, user `postgres.<project-ref>`, plus the database password you chose. Do not use the
   transaction pooler (port 6543): it drops session state, which Flyway's migration lock relies on. The apps create their own schema.
2. **Render**, per app: *New → Blueprint →* pick the repo. It asks for `DB_URL`, `DB_USERNAME`, `DB_PASSWORD`:
   - `DB_URL` = `jdbc:postgresql://<pooler-host>:5432/postgres?sslmode=require&currentSchema=<schema>` (schema from the table)
   - `DB_USERNAME` = `postgres.<project-ref>`, `DB_PASSWORD` = the database password (typed in Render only, never in chat or Git)
   Everything else, including the JWT secret and the private admin password, is generated by Render. After the first deploy the
   service answers on `https://<service>.onrender.com`; read `ADMIN_PASSWORD` in its *Environment* tab.
3. **Vercel**, per app: *Add New → Project →* pick the repo, set **Root Directory** to `frontend`, leave the framework as *Other*
   (`vercel.json` holds the build command and output folder). Deploy. Angular needs Node 22 or newer: if the build complains, set Node.js Version to 22.x in the project's settings.
4. Open `https://<project>.vercel.app`, log in with the demo accounts from the app's README, or the admin with the generated password.

## Know before you rely on it / قبل ما تعتمد عليه

- **Cold start.** Render spins a free service down after 15 minutes without traffic and wakes it on the next request. These APIs
  start in about 19 s with a full CPU, but the free plan gives 0.1 CPU. Measured locally on Masar Pro with a hard 0.1-CPU, 512 MB limit:
  **285 s** with the default JVM, **163 s** with the flags in `render.yaml`. Render's real throttling may differ, so time the first
  wake-up on the real service. Vercel's proxy gives up after 120 s, so the first request after a sleep can fail and a refresh
  a minute later works. Keeping a service always awake means a paid Render plan; free hours (750 per workspace per month) only cover one service
  running around the clock, not three.
- **Rate limits.** Visitors reach the API through Vercel's few server addresses, so `render.yaml` raises the per-IP anti-spam limits.
- **Supabase** pauses a free project after one week without activity (it can be resumed from the dashboard), keeps 500 MB, and allows
  two active free projects.
- **Vercel Hobby** is for non-commercial personal use: a portfolio demo is fine; adding ads or taking real payments is not.
- **Demo reset.** There is no nightly job on this stack. To reset one app: run `drop schema <schema> cascade;` in Supabase's SQL editor,
  then restart its Render service; Flyway recreates the tables and the demo data.
- **Updates.** CI publishes a new `latest` image on every merge to `main`, but Render does not redeploy a prebuilt image by itself:
  use *Manual Deploy* in the Render dashboard after each merge.
- **Payments** stay on the built-in sandbox gateway until you add test keys in Render's Environment tab.

Tested locally: the same image against a PostgreSQL using `currentSchema` + `SPRING_FLYWAY_SCHEMAS` (schema created, tables migrated, demo
data seeded, logins work) with the `render.yaml` JVM flags. Not tested here (no access from this environment): Render, Vercel and Supabase
themselves. `vercel.json` and `render.yaml` follow the vendors' documentation; the first real deploy is the test.
